## 一句话结论
「评审团」架构虽然把模型找证据的能力提了上来，但由于放弃了跨维度互斥仲裁、硬套了不兼容短对话的「单点封顶 3.5」与「<4 条强制 N/A」规则，加上缺失交付物上下文，目前呈现**「同一句话四处刷分、资深高手因提问精炼被逆向惩罚、三种评分模式切换即引发空值事故」**的半成品状态，信度（单次裸奔）和区分效度（聊天台资深与一般同为 3.63）均未达招聘选拔标准。

## 最该改的问题（按价值排序，5–8 条）

### 1. 评审团彻底丢弃跨评委互斥与时间窗硬拦截，导致「一鱼四吃」分数通胀与资深/一般区分失效
* **问题**：评审团模式下不跑 `arbitrate()` 互斥仲裁和超级 Prompt 归并，也不受 `inWindow()` 代码强约束，同一句话在不同评委手里重复计分。
* **证据**：
  * `engine.ts` `assessFluency()`：当 `committee` 为 true 时，直接跳过 `arbitrate(evs, structMsgs, logs)`；`committeeJudge` 提示词明写“其他行为由别的评委负责，你不用管、也不用让”。
  * **样本（资深 PM）**：同一句原话 `「先别写成稿，帮我把底层数据理一遍，我来核对。」` 同时被评委 01 计入 `B1`（q=3）和 `B2`（q=4），被评委 02 计入 `B6`（q=4）和 `B11`（q=3）；另一句 `「缓存命中已经包含在报表值里，所以真实值应该是 报表值×(1−缓存占总量比例)」` 同时在 `B16`（评委03，q=5）、`B24`（评委05，q=5）、`B15`（评委07，q=4）拿分，且 `B15↔B16` 在 `spec-v3.json` 中明文规定互斥！
  * `给宇宁-20261120.md`：聊天考试台评审团整体分数偏高，资深和一般都是 `3.63` 完全分不开。
* **影响**：严重破坏**结构效度与区分效度**。一般候选人只要在开场发一段包含目标、边界、角色、格式的常规结构化 Prompt，就能在 4 个维度同时刷分，直接追平资深候选人；招聘方看到的 7 维画像全是同一句话的回声。
* **怎么改**：
  1. 在 `engine.ts` 的 `assessFluency()` 中，将 `arbitrate(evs, structMsgs, logs)` 移到 `if (committee) {...} else {...}` **之后**作为公共收口步骤执行。
  2. 补齐 `标准—实现对照表` 第 5 条缺失的 4 组互斥对到 `PAIRS` 数组：`['B6', 'B11', ...]`、`['B14', 'B15', ...]`、`['B9', 'B14', ...]`、`['B13', 'B15', ...]`。
  3. 评审团合分前加一道硬窗口过滤：对 `evs` 中 `src === 'chat'` 的证据调用 `inWindow(e.bid, e.i, a)`（先修好锚点按块计算），越窗证据直接标 `valid = false` 并写入日志。
* **工作量**：小

### 2. 单点封顶（3.5）与「不足 4 轮强制清零」联手惩罚高效资深者，天花板效应锁死专家段
* **问题**：高效候选人用 3 轮高质量对话解决战斗，却因为轮次少（连续两轮发言算相邻 `i - l0 <= 1`）触发单点封顶（最高 3.5），甚至已有 5 档铁证的行为被代码强行抹成 `null`。
* **证据**：
  * `engine.ts` `scoreBehavior()`：评审团模式下 `for (const i of at0) { if (i - l0 > 1) occTop++; l0 = i; }` —— 如果候选人在第 2 轮（`i=1`）和第 3 轮（`i=2`）连续两次高质量核查，`2 - 1 = 1` 不满足 `> 1`，`occTop` 仍为 1，直接砍到 `3.5`！
  * **样本（资深 PM）**：3 轮对话中，`B13`、`B14`、`B15`、`B16`、`B23` 全部拿到了 **2 条 4–5 档的独立证据**，但因为对话只有 3 轮（消息索引 0, 1, 2 必然相邻），全部被标 `capped: true` 锁死在 `3.5` 分；更荒谬的是 `B10`（主动迭代），评委已抓出 `q=5` 的铁证（`「缓存估算算反了……」`），却被 `assessFluency` 里 `if (b === 'B10' && chat.length < 4) s = { ...s, score: null }` 强行清成未观测！最终资深者总分 `3.45` 进不了专家段（4.0）。
  * **样本（新手 PM）**：`B1` 给 `q=1`，经 `min(1, 4) - 0.5` 算出 `0.5` 分且标 `capped: true`——对 1 档差评做“防偶然闪光封顶”完全违背测量学常识。
* **影响**：严重扭曲**效度**。逼着聪明人为了刷分去水轮次、拆碎提问；招聘方看到资深者满屏 `3.5` 分和“主动迭代未观测”，与实际表现严重背离。
* **怎么改**：
  1. **修复低分误扣**：`scoreBehavior()` 封顶条件改为仅当 `q_max >= 4` 时生效（1–3 档本来就不是高分闪光，绝不减 0.5）。
  2. **废除相邻轮次连坐**：在 `committee` 模式下，每轮用户消息已是完整回合，将 `if (i - l0 > 1)` 改为 `if (i !== l0)`（只要在 ≥2 条不同消息，或 1 条对话 + 1 条工作台操作事件 `i < 0` 中均达到 `q >= 4`，即视为多次印证，不封顶）。
  3. **修改 `<4` 条的 N/A 逻辑**：`assessFluency()` 中改为 `if (NEED_4.has(b) && chat.length < 4 && !s.evidence.length)` 才置 `null`——没观测到时免责 N/A，**已经观测到高阶证据（如资深样本 B10 的 q=5）绝不抹杀**。
* **工作量**：小

### 3. 评审团漏传交付物正文，且量表死扣教科书式 Prompt（如必设角色），导致误判与迂腐建议
* **问题**：`committeeJudge` 的 Prompt 完全没传 `inp.deliverable`，导致需要核对交付物落地的指标全部盲判；同时锚点死绑“角色设定”，把务实的资深专家打成低分短板。
* **证据**：
  * `engine.ts`：对比 `judge()`（传了 `## 交付物（节选，B7 / B12 / B17 要核对是否落地）`）与 `committeeJudge()`（`prefix` 里只有任务、平台记录 `facts` 和对话 `transcript`，**完全漏掉了 `inp.deliverable`**）。
  * **样本（资深 PM）**：`B7` 评委在 `why` 中无奈写出：`「最终交付物不可见，无法确认落地，给4档」`，叠加封顶变 `3.5` 分；`narrative.interview` 甚至据此生成了错误的面试追问原因：`「交付格式与结构要求的最终交付物不可见」`。
  * **样本（资深 PM）**：候选人清晰设定了分步协作流并严格执行，只因没写“你是一位XX专家”，`B11` 被照 `spec-v3.json` 锚点打 `q=3` → 封顶 `2.5` 分，并在 `gaps`（待提升）中建议候选人补写 `「数据核算助理」` 这种对现代大模型毫无实质增益的套话。
* **影响**：直接拉低报告对**业务招聘方的专业信任度**。业务主管看到系统批评一个严谨对账的高手“没给 AI 设定角色”，且声称系统里明明存在的交付物“不可见”，会认为评测外行。
* **怎么改**：
  1. 在 `committeeJudge()` 的 `prefix` 中补入 `## 最终交付物（节选，供 B7 / B12 / B17 / B22 核对是否落地与占比）\n${clip(inp.deliverable, 2000)}`。
  2. 修订 `spec-v3.json` 中 `B11` 的 `a4`/`a5` 锚点与 `hint`：将“角色 + 交互方式 + 阶段衔接”改为“交互方式/控制权边界 + 阶段衔接规则（角色设定为可选加分，非必需）”，兑现提示词里“看实际效果，不看措辞；不要求教科书说法”的承诺。
* **工作量**：小

### 4. 评审团与 `v3` 单次温度 0 裸奔、截断无感知，与 `ai_use` 的多次重评信度机制割裂
* **问题**：同一平台内，`grader.ts` 的 `analyzeAiUse` 有双跑取均值 + 分差 >10 触发三跑取中位数 + `spread` 监控，而更复杂的 25 行为 `assessFluency` 只跑 1 次；且长消息截断只留头不留尾。
* **证据**：
  * `grader.ts`：`const runs = await Promise.all([runOnce(), runOnce()]); if (... > 10) runs.push(await runOnce());` 并记录 `runs` 和 `spread`。
  * `engine.ts`：`askJson` 用 `temperature: 0` 跑单次，一旦主模型 `claude-opus-5-5` 超时或 JSON 挂掉，静默降级到 `'qwen3.7-plus'`（见 `for (const m of [MODEL, 'qwen3.7-plus', 'qwen-plus'])`），**不同候选人甚至同一候选人重跑可能由完全不同的模型打分**，且 `rep.model` 永远写死常量 `MODEL`，日志里看不出实际用了兜底模型！
  * `engine.ts` `committeeJudge`：`clip(chat[i].q, 700)` 直接 `s.slice(0, n)` 砍掉 700 字以后的内容（而 `judge` 里好歹用了前 33% + 后 67%），候选人贴完一段 600 字数据后在末尾写的**核心指令和核查标准直接被切没了**。
  * `标准—实现对照表` 第 6 条：“理由里自述「不成立」却给分，目前没有专门拦”。
* **影响**：**评分信度（Reliability）失控**。长 Prompt 候选人核心指令被静默腰斩；跨模型静默回退会导致分数分布发生系统性漂移却无从排查。
* **怎么改**：
  1. **修复截断**：把 `committeeJudge` 的 `clip` 改为保留头尾（如前 300 字 + `…` + 后 500 字，因为 Prompt 的约束/格式要求90%在末尾）。
  2. **记录真实模型与自相矛盾拦截**：`askJson` 返回实际命中的 `model_id` 写入 `rep.model`（若触发降级在 `warnings` 告警）；在 `committeeJudge` 解析结果时增加正则校验：若 `why` 命中 `/(不成立|未体现|不属于|没有体现|不算)/` 且未出现转折词，强制丢弃该条证据。
  3. **关键边界重评**：不需全量双跑，仅当 `overall` 落在段位分界线 `±0.15` 内（如 `2.85–3.15` 熟练者线、`3.85–4.15` 专家线）时，对有分歧的维度重跑一次取中位数。
* **工作量**：中

### 5. 三种评分方式（`full` / `ai_use` / `fluency`）切换口径不一致，且两个 AI 分数尺度错位
* **问题**：代码注释承诺底座数据“不管选哪种都照常算、切回来都在”，但实际上 `fluency` 是按需计算的；且 `ai_use` 与 `fluency` 对同等级水平打出的百分制分数存在严重系统偏差。
* **证据**：
  * `scale.ts` 第 4 行注释写明：`「底座三层不管选哪种都照常算、照常存；这里只决定报告、成绩单和排序用哪部分，切回来都在。」` 但第 10 行 `desc` 和 `grader.ts` 第 258 行却是：`scale === 'fluency' ? fluencyOf(...) : Promise.resolve(undefined)`——管理员一旦从 `full` 切到 `fluency`，历史交卷在 `mainScore()` 下 `s.report?.fluency?.score100` 全是 `null`，在 UI 上经 `noAiLabel()` 会直接误显示为 **`「没用 AI」`**！
  * 分数映射错位：`ai_use` 1–5 档乘 20，`L4` 门槛是 `90` 分（4.5 档）、`L3` 是 `75` 分（3.75 档）；`fluency` 0–5 分乘 20（`score100 = Math.round(shown * 20)`），`专家` 门槛是 `4.0`（80 分）、`熟练者` 是 `3.0`（60 分）。更严重的是单条证据封顶 3.5 时，`ai_use` 给 `70` 分（仅 L2 中游），`fluency` 给 `70` 分却是稳居“熟练者”。
  * `grader.ts` `analyzeAiUse` 接口注释写：`「每条扣 8 分，最多 24」`，实际代码早已改成 `conduct / integrity(封顶40) / veto`，死注释误导维护。
* **影响**：对**平台管理员与招聘 HR** 造成严重线上事故隐患（切换开关导致全站旧榜单变成“没用 AI”），且客户试用不同模式时对候选人水平认知混乱。
* **怎么改**：
  1. 修 `scale.ts` 的 `noAiLabel` 与状态判断：区分 `report.fluency === undefined`（显示“未按此量表评估，点击补评”并提供后台批量重算按钮）与 `status === 'not_assessable'`（才走没用 AI / 无法评价逻辑），删掉 `scale.ts` 第 4 行的错误注释。
  2. 对齐百分制段位线：统一 `L1–L4` 与 `新手/发展者/熟练者/专家` 的锚点映射（如统一以 80 分为高阶/专家线，60 分为熟练/合格线）。
* **工作量**：小

### 6. 聊天考试台缺乏「沉默核查」观测手段，导致资深者与一般者拉不开差距
* **问题**：聊天考试台上没有工作台事件（打开源文件、运行测试等），资深者心算或看材料核查后只把改好的结论写进交付物，对话里没留痕，量表无法识别，甚至基线项判 0 分。
* **证据**：
  * `给宇宁-20261120.md`：`「聊天考试台上，资深和一般还是分不开，这和第二版看到的一样，资深的人很多核查不说出口」`（两者均为 `3.63`，而有 `ws_*` 事件的 AI 工作台则是 `4.03` vs `2.73`）。
  * `engine.ts` `locate()`：对普通文档台（非 `agent` 台），只统计了一条粗糙的 `B23-事件:采纳后自改`（`after.length && delta >= 20`），而 `grader.ts` 里明明已经有现成的 `ai_numbers_carried`（AI 算的数字进交付物）和 `verbatimRatio` / `grams`（8字片段重合率）以及 `open_material` 事件！
* **影响**：聊天考试台**选拔效度失效**（3.63 vs 3.63），无法区分“真正在线下核查并重写交付物的资深者”与“嘴上套路多的一般候选人”。
* **怎么改**：
  1. 把 `grader.ts` 中成熟的交付物比对信号下沉复用到 `engine.ts` 的 `locate()` 生成 `src: 'event'` 事实证据：
     * 若 `open_material` 发生在 AI 给出回答之后、且随后 `edit` 交付物修改了 AI 原回答中的数字/结论 → 生成 `B13/B23` 过程事件证据（“AI 回答后回看原始材料 X 次并修改交付物”）。
     * 计算 AI 回答与最终交付物的差异：若 AI 回答中有错漏（结合题目 `stages.calc` 参考值或材料原文），而候选人最终交付物里修正了该数值且未在聊天中明说 → 生成 `B23` 强证据（“AI 输出存在偏差，候选人在最终交付物中自行修正正确”）。
  2. 按块切分工作台事件：修复 `标准—实现对照表` 中“事件类证据目前整场汇成一条、归最后一块”的问题，按事件时间戳 `e.t` 归入对应的 `TaskBlock`，让工作台多阶段动作能正常跨块解封顶。
* **工作量**：中

### 7. 纯 AI 报告隐藏「交付物质量」，会让“高驾驭过程 + 烂交付结果”的候选人误导招聘方
* **问题**：当平台开启 `ai_use` 或 `fluency` 模式时，前端完全隐藏回答质量（`result`）和 AI 基线对比，但 `fluency` 报告的“用人建议”却敢直接给出岗位胜任力结论。
* **证据**：
  * `scale.ts`：`aiOnly` 注释 `「只看 AI 那一类（不显示回答质量、过程评价、AI 基线）」`，`mainScore` 只取 `fluency.score100`。
  * **样本（资深 PM）**：`narrative.summary` 坦承 `「路线图本身的设计质量在这份记录里看不到」`，但在下方 `advice.fit` 依然给出了具体的业务任务推荐。如果一个候选人非常擅长向 AI 提问、设边界、挑小刺（拿到 `fluency` 80 分），但最终交上去的业务方案核心测算全错（`result.total` 只有 35 分，还不如 AI 裸跑基线），招聘方在榜单上看到的仍是排第一的 80 分！
* **影响**：对**招聘决策**产生高危误导——企业招人终究要看能不能把活干对（结果效度），纯看沟通姿势极易招到“Prompt 表演家”。
* **怎么改**：
  1. 在 `engine.ts` 的 `narrate()` 输入中，传入 `result.total` 及未通过的核心 rubric 条目摘要（仅用于校验，不改 `fluency` 分数）：当 `fluency >= 3.5` 但 `result.total < 60`（或低于 AI 基线）时，强制在 `narrative.advice.verdict` 触发风险提示：“AI 协作规范度高，但最终业务交付物未达标（低于参考基线），需警惕形式大于实质”。
  2. 在 `ai_use` / `fluency` 模式的成绩单列表页，保留 `fluency` 作为主排序分，但增设一列轻量标签「交付物达标线：通过 / 低于 AI 基线 / 未达标」（由 `grader.ts` 已经算好的 `result` 和 `compare.delta` 直接派生，零额外 LLM 成本）。
* **工作量**：小

## 先别动的（2–3 条，说明理由）

1. **先别上多模型/全量双跑 `assessFluency`**
   * **理由**：`committee` 模式一次评估已经要调 `1（任务画像）+ 7（维度评委）+ 1（总评解读）= 9` 次大模型。在单点封顶、跨评委互斥这些**确定性规则 Bug** 没修好之前，全量双跑只会让 Token 成本和延迟翻倍（逼近接口 300s 超时红线），却救不回规则本身导致的系统性偏差。
2. **先别用 LLM 语义切块（`task_segment_llm.py`）替换平台现有的 `taskBlocks()`**
   * **理由**：平台已有确定的产品结构边界（`stage_unlock` 推进步骤、`switch_part` 切换交付物、外部 AI 切换工具），这是 100% 稳定可复现的硬锚点。引入千问做语义切块会带来新的信度波动（切多一块少一块直接决定 `b=1` 还是 `b=2` 封不封顶），切块工具留给线下无埋点的纯文本数据集做研究即可。
3. **先别开启 `spec-v3.json` 里默认关闭的条件自评表单（S2 / S3 / S4 / S5）**
   * **理由**：目前交卷时的必填/选填项（`S1` AI 参与说明 + `next_step` 再给一天先改哪）已经能有效抓出诚信负向（如新手样本 `B22` 淡化 AI 贡献得 1.5 分）。若在考试交卷瞬间再弹出工具选择、伦理偏差、跨领域迁移等一堆事后自评问卷，极易诱发候选人“事后找补表演”，污染客观行为量表的纯度。

## 需要业务方拍板的问题（只列真正要人决定的）

1. **单任务（单块）题目的「专家段（≥4.0）」准入标准怎么定？**（对应《给宇宁》的核心卡点）
   * **现状死结**：平台大量题目是单交付物（只有 1 个任务块）。若死守 02 页“同块只算 1 条，`b=1` 必封顶 3.5”，则**所有单任务题目的候选人永远不可能达到专家段（4.0）**。
   * **拍板选项**：
     * **方案 A（改规则，推荐）**：认可“同块内 ≥2 处不同轮次的高阶证据（或 1 处对话 + 1 处操作验证事件）”等同于稳定表现，解除 3.5 封顶；
     * **方案 B（改出题）**：维持跨块才解封顶，但强制规定凡启用 `fluency` 量表的考核任务，出题器必须拆成 ≥2 个推进阶段（`stages`）或 ≥2 份交付物。
2. **「少轮次、重线下心算核查」的资深专家，在纯 AI 量表里算高分还是算证据不足？**
   * **业务冲突**：像样本里的资深 PM，只问 AI 3 轮让它干脏活累活，核心判断全自己做，这在真实工作里是最优解，但在 `fluency` 量表里会因触发项少、对话短吃亏。
   * **拍板选项**：当候选人对话 ≤3 轮但最终交付物高分且修正了 AI 错误时，是允许通过“交付物反推核查”给高 `fluency` 分，还是明确告知客户“对话过短一律只出画像不出总分（标为独立完成倾向）”？
3. **平台两套 AI 评估体系（5 维 `ai_use` vs 7 维 `fluency`）长期的商业定位是什么？**
   * **业务冲突**：`ai_use` 绑定了企业/岗位定制的 `AiPolicy`（鼓励用还是慎用、治理红线、岗位权重），贴合 B 端招聘定制需求；`fluency` 是潜历的通用标准化 25 行为学术量表，不支持企业 `AiPolicy` 权重。两套并存导致研发维护两套相似逻辑且分数打架。需要定：未来是把 `AiPolicy` 融入 `fluency` 后废弃 `ai_use`，还是 `ai_use` 面向企业社招定制、`fluency` 仅面向校招/通用认证？
